# 006 CLI

CLI 是第一版的唯一入口，GUI 排在后面。

## 全局约定

### 选项

| 选项 | 默认 | 说明 |
| --- | --- | --- |
| `--json` | 关 | 以结构化 JSON 输出到 stdout，人类可读信息一律走 stderr 或不输出 |
| `--workspace PATH` | 见下方「工作区解析」 | 工作区根目录 |
| `--no-color` | 自动 | 关闭彩色（也识别环境变量 `NO_COLOR`） |

全局选项放在**子命令之前**：`capnest --workspace ./ws add skill ./x`。

`--json` 额外接受写在子命令之后（`capnest list --json`）——这是极常见的写法，两种位置等价。

### 工作区解析

工作区根目录按以下顺序确定，第一个命中的生效：

1. `--workspace PATH`
2. 环境变量 `CAPNEST_HOME`
3. 工作区根目录下 `config.yaml` 的 `workspace` 字段（相对该文件所在目录解析）
4. 当前目录

除 `init` 外，解析出的工作区必须已存在，否则退出码 8（`NOT_FOUND`）。`init` 的 `PATH` 参数直接指定要创建的工作区，不走上面的解析。

### 输出通道

- **stdout**：结果数据。`--json` 时是 JSON；否则是人类可读文本。
- **stderr**：诊断信息、警告、进度提示。`--json` 模式下 stderr 仍可有人类文本，但**不得混入 stdout**。

### JSON 协议

成功：

```json
{
  "ok": true,
  "command": "list",
  "data": {
    "assets": [
      {
        "id": "skills/sql-analysis",
        "type": "skill",
        "version": "1.0.0",
        "hash": "sha256:9f2c…"
      }
    ],
    "count": 1
  }
}
```

失败：

```json
{
  "ok": false,
  "command": "apply",
  "error": {
    "code": "CONFLICT",
    "message": "目标路径已存在且不由 CapNest 管理，拒绝写入",
    "details": {
      "conflicts": [
        {
          "path": "C:/Users/x/.claude/skills/foo",
          "reason": "not_owned"
        }
      ]
    }
  }
}
```

**路径等机器需要的数据一律放 `details`，`message` 只给人看。** 这样 GUI 不会被迫去解析自然语言。

### 错误码与退出码

| 退出码 | 名称 | 含义 |
| --- | --- | --- |
| 0 | `OK` | 成功 |
| 1 | `ERROR` | 一般失败 |
| 2 | `USAGE` | 命令行用法错误（Typer 默认） |
| 3 | `VALIDATION_FAILED` | `validate` 发现问题，或 `plan` 的前置校验不通过 |
| 4 | `DRIFT_DETECTED` | `status --strict` 检测到漂移或版本落后 |
| 5 | `CONFIRMATION_REQUIRED` | 存在破坏性变更但未给 `--yes` |
| 6 | `UNSAFE_CONTENT` | 隐藏 Unicode 扫描命中（阻断项） |
| 7 | `CONFLICT` | 目标冲突 / 归属证明失败 |
| 8 | `NOT_FOUND` | 资产、Profile 或部署记录不存在 |

同一份错误码表同时用于 `error.code` 字符串与进程退出码，方便脚本判断。

## `capnest init`

```
capnest init [PATH] [--force]
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `PATH` | `.` | 工作区根目录 |
| `--force` | 关 | 目录已存在且已有 `config.yaml` 时仍然初始化 |

**行为**：创建目录骨架与 `config.yaml`。目录已存在且已有 `config.yaml` 时**拒绝**（退出码 7），除非加 `--force`。

**创建的结构**：

```
<workspace>/
├── assets/
│   ├── mcp/
│   ├── skills/
│   └── workflows/
├── profiles/
├── state/
│   ├── deployments.json      # 初始内容 []
│   ├── ownership.json        # 初始内容 {}
│   ├── backups/
│   └── logs/
└── config.yaml
```

**退出码**：0 / 7（已存在）/ 1

## `capnest doctor`

```
capnest doctor [--target T,...]
```

**行为**：自检，不改任何东西。检查项：

1. Python 版本 ≥ 3.11
2. 工作区可发现且结构完整
3. 每个 target 的 home / config 文件是否存在、是否可读写
4. Agent CLI 是否在 PATH、版本号
5. **Adapter 能力矩阵**：每个 target 支持哪些资产类型与部署形态
6. 部署形态可用性：`symlink` 在当前系统是否可行（Windows 无开发者模式时明确提示不可用）

**分阶段实现**：M0 交付 1–4 的骨架（能力矩阵先给静态值）；5–6 在 M2 补全为真实探测。第 5、6 项在 M0 的 `--json` 输出里已经存在，值是「第一刀的真实能力边界」而不是占位符。

**输出**：`--json` 时

```json
{
  "ok": true,
  "command": "doctor",
  "data": {
    "checks": [
      {"name": "python_version", "status": "ok", "detail": "3.11.9"},
      {"name": "target.mcode", "status": "ok", "detail": "…"},
      {"name": "target.claude-code.mcp_backend", "status": "ok", "detail": "json"},
      {"name": "deployment.symlink", "status": "warn", "detail": "Windows 未启用开发者模式，仅支持 copy"}
    ],
    "capabilities": {
      "mcode": {
        "supports": ["skill", "mcp-server"],
        "deployment_modes": ["copy", "symlink"],
        "skills_path": "C:/Users/x/.minimax/skills",
        "mcp_backend": "yaml"
      }
    }
  }
}
```

`status` 取值：`ok` / `warn` / `fail`。有 `fail` 时退出码 1，只有 `warn` 时退出码 0。

## `capnest add`

```
capnest add <kind> <PATH> [--name NAME] [--force]
capnest add --from <target>:<name> [--kind KIND] [--force]
capnest add --from <target>:*
capnest add --from *
```

| 参数 | 说明 |
| --- | --- |
| `kind` | `skill` / `mcp` / `workflow` |
| `PATH` | 源路径，目录 |
| `--name` | 资产名，缺省用目录名 |
| `--from` | 从某个 Agent 侧收编既有资产 |
| `--force` | 已存在同名资产时覆盖 |

**行为**：

1. 扫描源目录，做**隐藏 Unicode 扫描**——命中即阻断，退出码 6
2. 读取或生成 `capability.yaml`：
   - 源目录已有 `capability.yaml` → 校验，不一致则报错
   - 没有 → **自动生成**一份最小 manifest（`kind: Capability`），`version` 默认 `0.1.0`，`description` 留空
3. 校验 `spec.entrypoint` 指向的文件确实存在
4. 复制到 `assets/<目录名>/<name>/`（copy 语义，不建立引用）
5. 计算内容哈希

**`--from` 收编**：`capnest add --from mcode:manim` 会从 `~/.minimax/skills/manim/` 复制进来，并**保留原 `SKILL.md` 不动**，只补一份 `capability.yaml`。这是「把 Agent 里已有的能力收编进 CapNest」的主路径。收编来的资产会在 `metadata.source` 里记下来源，`list` 的 SOURCE 列会显示 `Claude Code` / `mcode`。

**`--from <target>:*` 批量收编**：`capnest add --from claude-code:*` 把目标侧**所有**能收编的 skill 一次性收进来。

- 顶层没有 `SKILL.md` 的**容器目录**（一堆 skill 的集合）与目录里**还套着别的 skill** 的，都跳过并说明原因——v1 只支持单层 skill 目录。
- 含隐藏 Unicode 字符的**那一个**被跳过并记录，其余照常收编（单个收编 `add --from <target>:<name>` 仍然是命中即阻断，退出码 6）。
- 同名冲突的跳过并记录，其余不受影响。

**`--from *` 收编所有目标**：`capnest add --from '*'` 把两个目标侧能收编的 skill 一起收进来。
同名同内容的**只保留一份**（来源合并进 `metadata.sources`），同名不同内容的记成**冲突**，不覆盖。

**收编即认领**：收编成功时，目标侧那个目录会被记进 `state/ownership.json`——
从那一刻起 CapNest 就**管**这份能力了，之后 `apply` 才能把它更新成工作区里的版本。

**先看有什么**：`capnest inspect <target>` 列出目标侧已有的 skill 与它们的 STATE。

**副作用**：写 `assets/`。

**退出码**：0 / 6（不安全内容）/ 3（manifest 不合法）/ 7（同名冲突且无 `--force`）/ 8（源路径不存在）/ 1

## `capnest list`

```
capnest list [--type skill|mcp|workflow] [--sort name|type|version|source] [--source SOURCE]
```

| 参数 | 说明 |
| --- | --- |
| `--source` | 只列出某个来源的资产：`Claude Code` / `mcode` / `local` |

**行为**：扫描 `assets/`，输出资产清单。人类可读模式用 rich 表格；`--json` 模式输出结构化数组。

**输出示例**（人类可读）：

```
ID                        TYPE      VERSION  SOURCE        HASH
skills/sql-analysis       skill     1.0.0    local         sha256:9f2c…
skills/doc-coauthoring    skill     0.1.0    Claude Code   sha256:41ab…
mcp/database              mcp       1.0.0    local         sha256:7de0…
```

SOURCE 列读的是 `metadata.source`——本地创建的资产显示 `local`，从 Agent 侧收编来的显示来源目标。

**退出码**：0 / 1

## `capnest search`

```
capnest search <QUERY> [--type T] [--limit N]
```

**行为**：在 `metadata.id` / `metadata.name` / `metadata.description` / `spec.type` 上做大小写不敏感的子串匹配。

**v1 不做全文索引**：直接扫目录 + 内存过滤。资产过百再考虑数据库。

**退出码**：0（无结果也是 0）/ 1

## `capnest validate`

```
capnest validate [--asset ID] [--strict]
```

**检查项**：

| # | 检查 | 失败级别 |
| --- | --- | --- |
| 1 | `apiVersion` 与 `kind` 合法 | error |
| 2 | `metadata.id` 与所在目录一致（`skills/x` ↔ `assets/skills/x`） | error |
| 3 | `spec.type` 与目录类别一致 | error |
| 4 | `spec.entrypoint` 指向的文件存在 | error |
| 5 | `metadata.version` 是合法 semver | error |
| 6 | `spec.dependencies[].ref` 指向存在的资产 | error |
| 7 | 隐藏 Unicode 扫描 | error |
| 8 | 资产 ID 唯一 | error |
| 9 | `format` 在已知词表内 | warn（`--strict` 下升级为 error） |
| 10 | `spec.permissions.requested` 用了未知权限类别 | warn |

**输出**：逐条列出 `level` / `location` / `message`。`--json` 时 `data.violations` 为数组。

**退出码**：0（无 error）/ 3（有 error）/ 1（工作区都读不了）

## `capnest profile`

### `capnest profile create`

```
capnest profile create <NAME> [--asset ID]... [--target T]... [--force]
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--asset` | 无 | 要纳入 Profile 的资产 ID，可重复 |
| `--target` | `config.yaml` 的 `default_targets` | 部署目标，可重复 |
| `--force` | 关 | 已存在同名 Profile 时仍然覆盖 |

**行为**：生成 `profiles/<NAME>.yaml`，`kind: CapabilityProfile`。

- 未指定 `--asset` 时生成空 Profile，随后可手工编辑
- 未指定 `--target` 时取 `config.yaml` 的 `default_targets`
- 已存在同名 Profile 时拒绝（退出码 7），除非 `--force`
- 引用的资产不存在时拒绝（退出码 8），并在 `details.missing` 里列出缺哪些
- 目标名不在已知目标内时拒绝（退出码 3），并在 `details.unknown` 里列出

### `capnest profile list` / `capnest profile show <NAME>`

`list` 列出所有 Profile；`show` 输出单个 Profile 的详情，含引用资产的当前版本与哈希，以及**解析状态**（引用的资产是否都存在）。

**退出码**：0 / 8（不存在）


## `capnest inspect`

```
capnest inspect <TARGET> [--json]
```

**行为**：**只读**地盘点目标 Agent 侧现在有哪些 skill。这是「收编」的前置一步——要先知道目标里有哪些、叫什么名字，才谈得上 `add --from <target>:<name>`。

**输出**：

```
claude-code  (C:\Users\<user>\.claude\skills)
SKILL                        FILES  HASH                  STATE
access-sido-meet             2      sha256:e2e72535c7ef3  unmanaged
ai-research-skills           559    sha256:d8c163bd0cf3a  nested
paper-write-skill-workspace  14     sha256:a0be7fa289c33  container

收编其中一份：capnest add --from claude-code:<名字>
```

`STATE` 的四种取值：

| 值 | 含义 |
| --- | --- |
| `managed` | CapNest 已经 claim 了它（`state/ownership.json` 里有记录） |
| `unmanaged` | 目标侧已有、但不由 CapNest 管 |
| `nested` | 目录里**套着**别的 skill（子目录中还有 `SKILL.md`）——v1 不支持部署这种 |
| `container` | 顶层没有 `SKILL.md`，是一堆 skill 的容器目录 |

**退出码**：0 / 8（未知的目标）

## `capnest sync`

```
capnest sync [--target T,...] [--adopt] [--profile NAME] [--yes] [--dry-run] [--json]
```

**行为**：把两个 Agent 侧的能力收成一份，再同步回两边。四步各有边界：

1. **收编**（`--adopt`）：复制目标侧的 skill 进工作区，原文件不动。
   同名同内容自动去重（只留一份，来源合并）；同名不同内容记成冲突，不覆盖。
2. **去重**：内容相同、名字不同的资产只报告，不自动合并。
3. **冲突**：工作区与目标侧内容不同。**没有裁决的冲突不写那个目标**，
   其余照常同步——一处分歧不该拖住全局。
4. **同步**：把工作区里的资产写回每个目标。写之前照旧做归属检查：
   证明不了归属的既有路径一律拒绝。

同步是**幂等**的：内容一样就不写，重复执行不动 mtime。

**输出示例**：

```
收编 25 个 skill（去重 1，冲突 0，跳过 2）
待同步资产 25 个 → 目标 mcode, claude-code
  = 重复内容：pdf  =  pdf-tools
已同步 2 个目标
校验：一致 50，不一致 0
```

**退出码**：0 / 7（有未裁决的冲突，或目标路径无法证明归属）/ 5（要写但没加 `--yes`）/ 6（不安全内容）

## `capnest conflict`

```
capnest conflict list [--target T,...] [--json]
capnest conflict resolve <ASSET> --use workspace [--target T,...] [--json]
capnest conflict resolve <ASSET> --use <target>:<name> [--json]
```

**冲突**= 工作区里的资产与某个目标侧同名目录**内容不同**。
CapNest 不替用户决定哪一份对，它只把分歧摆出来，并记住裁决。

| 裁决 | 含义 | 副作用 |
| --- | --- | --- |
| `--use workspace` | 以工作区为准 | 认领目标路径（`ownership.json`），下次同步覆盖目标 |
| `--use <target>:<name>` | 以目标为准 | 目标侧内容**拉回**工作区，保留工作区自己的 `capability.yaml` |

裁决记在 `state/conflicts.json`，所以同步可以重复执行——下一次不用再问一遍。

**退出码**：0 / 7（未知的目标）/ 8（资产或目标侧目录不存在）

## `capnest dedupe`

```
capnest dedupe [--json]
```

**行为**：**只读**。报告**内容相同、名字不同**的资产组。
同名同内容的重复在收编时就已经去掉了，这里报的是另一类——
两个名字内容一样，往往是用户**有意**放了两份，所以只报告、不自动合并。

**退出码**：0

## `capnest plan`

```
capnest plan --profile <NAME> [--target T,...] [--json]
```

**行为**：**只读**。计算并展示将要发生的变更，**不写任何文件**（连日志都不写）。

**步骤**：

1. 加载 Profile，校验引用的资产都存在（缺失 → 退出码 3）
2. 对每个 target：读当前状态（`Adapter.read()`）→ 归一化 → 与期望状态比对 → 生成 `WriteIntent` 列表
3. 对每个 `WriteIntent` 生成 diff
4. 展示：按 target 分组，逐项标注 `create` / `update` / `unchanged`

**输出示例**：

```
mcode
  ~ config.yaml
    + mcpServers.database  (new)      # 落点待实测确认
  ~ skills/sql-analysis/  (new)
    + SKILL.md
    + capability.yaml

claude-code
  ~ .claude.json
    + mcpServers.database  (new)
  ~ skills/sql-analysis/  (unchanged)
```

**与 `apply` 的一致性约束**：`plan` 与 `apply` 必须接受相同的 `--profile` / `--target`，并共用同一套 diff 计算函数。`apply` 若无法复现最近一次 `plan` 的作用范围，拒绝执行。

**退出码**：0 / 3（前置校验失败）/ 1

## `capnest apply`

```
capnest apply --profile <NAME> [--target T,...] [--yes] [--dry-run]
```

**行为**：

1. 重复 `plan` 的全部计算（共用同一函数）
2. **隐藏 Unicode 扫描**（阻断）
3. **归属检查**：目标路径已存在但未被 CapNest claim → 退出码 7，不写入
4. **预写事务**：把新内容写到临时文件，不动目标
5. **确认**：存在破坏性变更（`update` / 任何写入）且未给 `--yes` → 打印将要执行的内容并退出码 5
6. **提交**：逐项「备份原文件 → 原子替换 → 校验指纹」
7. 写入 `state/deployments.json` 一条 `DeploymentRecord`，含 `applied_paths` / `backups` / `created_paths` / `asset_hashes`

**`--dry-run`**：等价于 `plan`，但走完整的前置校验（含归属检查与 Unicode 扫描），用于 CI。

**第一刀不做删除**：目标上多出来的文件只报告、不移除，`plan` 里标注 `[skipped: removal not supported in v1]`。

**事务边界**：所有目标先全部 stage，再逐个 commit；任何一个 commit 失败，其余全部 abort——要么都没写，要么都写完整。

**第一刀的记录里没有 `applied_state_hash`**：漂移检测靠「目标目录内容哈希 vs 记录里的资产哈希」比较，第二刀再引入独立的状态哈希。

**退出码**：0 / 3 / 5 / 6 / 7 / 1

## `capnest status`

```
capnest status [--profile P] [--target T,...] [--strict]
```

**行为**：对照 `state/deployments.json` 汇报状态。

| 状态 | 判断依据 |
| --- | --- |
| `up-to-date` | 目标目录内容哈希 == 记录里的 `asset_hashes` |
| `drift` | 目标目录内容哈希 != 记录里的 `asset_hashes`——**Agent 侧被外部改了** |
| `version-lag` | 资产哈希 != `asset_hashes`——**CapNest 里的资产更新了** |
| `never-deployed` | 该 target 没有部署记录 |
| `failed` | 最近一次部署的 `phase_status` 里有 `FAILED`（第二刀才有 `phase_status`） |

**两种检测必须分开报**：漂移比目标状态哈希，版本落后比资产哈希。

**输出示例**：

```
TARGET          PROFILE      STATUS         DETAIL
mcode          data-agent   up-to-date
claude-code     data-agent   drift          .claude.json 被外部修改
mcode          data-agent   version-lag    skills/sql-analysis 1.0.0 → 1.1.0
```

`--strict`：存在 `drift` 或 `version-lag` 时退出码 4，否则 0。

**退出码**：0 / 4（`--strict` 下有漂移）/ 1

## `capnest rollback`

```
capnest rollback --target <T> [--yes] [--to <deployment-id>]
```

**行为**：把某个 target 恢复到最近一次成功部署**之前**的状态。

1. 找到目标部署记录（默认该 target 最近一条成功记录）
2. 从 `state/backups/<timestamp>/<target>/` 还原文件
3. 删除该次 `apply` **新建**的路径（`created_paths` 中记录）
4. 从 `state/deployments.json` 移除该记录
5. 释放对应的归属 claim

**不做的事**：不回滚已经被用户在 Agent 侧手工改动过的内容——那属于漂移，应该由用户先决定。

**`--yes`**：接受但**不要求**——回滚只动 CapNest 记录过的路径（还原备份、删除本次新建的路径、释放归属），不会碰用户自己的内容。

**空目录清理**：如果目标的 skills 目录在回滚后完全为空，它会被一并删除——这样目标目录能回到部署前的状态。

**退出码**：0 / 8（没有可回滚的记录）/ 1

## `--json` 的稳定契约

以下字段是**对外承诺**，GUI 与 Agent 依赖它们，不得随意改名：

| 路径 | 保证 |
| --- | --- |
| `ok` | 恒为布尔 |
| `command` | 恒为命令名 |
| `data` | 成功时存在，结构按命令定义 |
| `error.code` | 失败时存在，取值见上文错误码表 |
| `error.message` | 面向人的一句话 |
| `error.details` | 面向机器的结构化数据，**永远不要把路径塞进 message** |

新增命令时，`--json` 输出**必须**与人类可读输出同时提供，不允许只做其中一种。
