# 000 Philosophy

CapNest 的核心主张：

**能力属于人，不属于 Agent。**

## 要解决的问题

今天每个 Agent 都有自己的 Skill、MCP、Plugin 和配置管理机制：Codex 有自己的一套，Claude Code 有自己的一套，其他 Agent 也各有各的。于是使用多个 Agent 的人只能在每个 Agent 里重复配置、复制和维护同一批能力。

这些能力本质上属于用户，却被托管在某个 Agent 的配置目录里。换个 Agent、换个机器，就要重建一遍。这是**能力归属错位**。

CapNest 做的事只有一件：**把个人积累的 AI 能力从 Agent 中解耦出来，形成独立的、可持续积累的资产，并让同一份资产在多个 Agent 上保持完全一致。**

## 四个价值

| 价值 | 含义 |
| --- | --- |
| Persistence | 能力独立存储，不依附于某个 Agent |
| Composition | MCP、Skill、Workflow 组合成 Profile，形成可复用集合 |
| Portability | 一份资产适配多个 Agent，统一管理版本、部署与回滚 |
| Discovery | Agent 可以查询并申请使用已有能力（远期） |

## 目标用户

第一阶段只有一个画像：**同时使用多个 Agent 的重度 AI 用户**。白天用 Codex 写代码，晚上用 Claude Code 做论文调研，两边需要同一套「SQL 分析」「数据库 MCP」「论文评审」。

这类用户的痛点不是「没有能力」，而是**能力无法沉淀、无法迁移、无法保持版本一致**。

## 边界

CapNest 位于 Agent Runtime 之下，关注它们**之下的公共能力资产层**。

| CapNest 做什么 | CapNest 不做什么 |
| --- | --- |
| 能力的登记、组合、版本化 | Agent 运行时、会话、任务编排 |
| 能力在多个 Agent 之间的一致部署 | 公共能力市场、组织级治理与合规 |
| 部署前的差异预览与部署后的回滚 | Skill / MCP / Plugin 的原生格式本身 |
| 能力的检索与（远期）申请 | Workflow 的执行引擎 |

### 非目标

明确不做，避免项目膨胀：

- 不做通用 Agent Runtime
- 不做 Agent Workspace / 会话管理
- 不做公共 Marketplace（远期）
- 不做 Workflow 执行引擎（首期只登记）
- 不做通用包管理器
- 不重造 Skill / MCP / Plugin 的原生格式

## 已定的取舍

下面每条都是**设计决策**，不是待办。

| 能力 | 决策 | 理由 |
| --- | --- | --- |
| 依赖范围求解 | 自建轻量版本，仅 semver 约束 | 通用包管理器已占位；我们的模型是「本地目录 + 约束」，不需要包图 |
| Lockfile | 自建，字段为 `resolved` / `source` / `hash` / pin | 与 Manifest 协同需要独立演进 |
| Diff / Apply / Rollback | 自建 | 没有现成方案提供部署前 diff 与回滚语义 |
| 漂移检测 | 自建，与版本落后分离 | 两种机制回答不同问题，混在一起会误报 |
| 安全扫描 | 自建（隐藏 Unicode 等） | 检测项明确，实现成本低 |
| 插件包 | 只做兼容读取，不作为部署形态 | 插件目录由 marketplace 缓存管理，直接写入会与重装机制打架 |
| 资产索引 | 文件系统扫描，不引入数据库 | 个人规模资产量级下，扫目录足够，且避免双写一致性 |
| GUI | 自建，通过 `capnest --json` 与核心通信 | 不引入 Python sidecar，一套协议两处用 |

## 原则

1. **统一描述，不强制统一执行。** 尤其 Workflow 不为了统一而兼容所有执行引擎。
2. **文件是事实来源。** 状态与索引都可从文件重建。
3. **无法证明归属的文件一律不碰。** 见 [004 Deployment](004-deployment.md)。
4. **先看差异，再落盘。** 部署前必须有可读的 diff，改动前必须有备份。
5. **CLI 是唯一入口。** GUI 与 Agent 复用同一套核心与同一份输出协议。
